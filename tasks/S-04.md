# S-04 · Settle → claim → activate (gated)
Sprint 1.0 · Layer: L2a · Depends on: S-03 (done), S-05 pattern (buy.ts) · PRD: docs/PRD-1.0-sprint.md §3 (Staking, CREDIT), §4 T-4, §6 · MONEY TICKET → Code → Audit → Test

## Goal
CREDIT earned by the staked position reaches the Treasurer's API balance without a human: `settle` finalized periods, `claim` the minted CREDIT, `activate` it for the hot wallet's key — gated, capped, every step in the ledger with its tx hash; and when the staker key is absent, the same code produces an exact manual to-do instead.

## In scope
- `packages/core/src/chain/claim.ts`, mirroring S-05's structure (`planClaim` pure → `executeClaim` against a narrow client interface → `claimAndActivate` orchestrator writing ledger rows, idempotency key = tick bucket). Do NOT modify `buy.ts`.
- Period discovery: `PERIOD()` = 3600 s and `genesisTime()`/`currentPeriodStart()` are UNVERIFIED selectors (PRD §3) — do not call them. Use `rewardPeriod(id)` (verified, returns 5 uint256) by probing ids backwards from an env `STAKING_LAST_PERIOD_HINT` or by binary search on `rewardOf(staker, id)` > 0 within the last 168 ids; record what `rewardPeriod` returns for 3 ids in `docs/api-notes.md` and derive which field is the period start. If that cannot be determined in 45 min, fall back to: `settle([])` is NOT allowed; instead expose `settle(periodIds)` with ids supplied by env `STAKING_SETTLE_PERIODS` (comma list) and document it as manual — put the exact question in Blocked on.
- Flow when `STAKER_PRIVATE_KEY` is set: `settle(ids)` (staker) → `claim()` (staker, returns minted amount) → `CREDIT.activate(amount, bytes32(hot))` (staker). Each tx waits 1 confirmation, receipt status checked, `Activated` event decoded (CREDIT ABI) for the activate step. Gates: `TREASURER_LIVE`, `ACTIVATE_MAX_PER_DAY` (default 50 CREDIT = 50e6 atoms, in `policy/defaults.ts`, env may only lower), `MIN_GAS_ETH` on the staker wallet.
- Flow when only `STAKER_ADDRESS` is set: read `settledOf(staker)` and `CREDIT.balanceOf(staker)`; if either > 0, write ONE `alert` treasury event per tick bucket with `meta.manual = {step: 'settle'|'claim'|'transfer', amount, explorerWriteUrl}` (robin.etherscan.io write-contract link) — this is the "manual fallback" the page shows. If `CREDIT.balanceOf(hot)` > 0 and live: `activate(amount)` from the hot wallet (this path needs only `TREASURER_PRIVATE_KEY`).
- CLI `pnpm treasury:claim [--live]` with the same `yes-send` guard as S-05.
- Ledger rows: `dry_run` (with plan) or `settle`/`claim`/`activate` rows with tx hashes; `alert` rows for manual steps.

## Out of scope
- `unstakeAll`/exit (never). Buying (S-05). Policy timing (S-06). Stake-up (S-07).

## Acceptance criteria
1. `planClaim` table-driven tests: live off → dry-run plan; nothing claimable → no-op plan; claimable > cap → capped activate amount with the remainder left in wallet; staker key absent → manual alert plan with correct step; gas floor.
2. `executeClaim` against a fake client: settle→claim→activate called in order with exact args (activate beneficiary = bytes32 hot); a reverted receipt at any step stops the chain and records what completed.
3. Ledger: dry-run → 1 row; full success → 3 rows sharing `meta.idempotencyKey`, each with its own tx_hash; re-call with the same key → no new rows.
4. Live off end to end against the fake client → `writeContract` call count 0.
5. No private key in logs/errors/meta/CLI output.
6. Period discovery documented in api-notes with 3 real `rewardPeriod` reads (live, read-only), or Blocked on filled with the exact question.
7. Live: not in this ticket (first live run is S-06 with So's `ok live`).

## Audit focus
Which wallet signs which tx (staker vs hot); activate beneficiary; caps in CREDIT atoms (6 dp) never 18 dp; period id off-by-one (settling an unfinalized period reverts — fine — but never skipping a finalized one silently); manual-alert spam (one per bucket); idempotency.
