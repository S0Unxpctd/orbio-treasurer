# S-04 · Settle → claim → activate (gated)
Sprint 1.0 · Layer: L2a · Depends on: S-03 (done), S-05 pattern (buy.ts) · PRD: docs/PRD-1.0-sprint.md §3 (Staking, CREDIT), §4 T-4, §6 · MONEY TICKET → Code → Audit → Test

## Goal
CREDIT earned by the staked position reaches the Treasurer's API balance without a human: `settle` finalized periods, `claim` the minted CREDIT, `activate` it for the hot wallet's key — gated, capped, every step in the ledger with its tx hash; and when the staker key is absent, the same code produces an exact manual to-do instead.

## In scope
- `packages/core/src/chain/claim.ts`, mirroring S-05's structure (`planClaim` pure → `executeClaim` against a narrow client interface → `claimAndActivate` orchestrator writing ledger rows, idempotency key = tick bucket). Do NOT modify `buy.ts`.
- Period discovery: `PERIOD()` = 3600 s and `genesisTime()`/`currentPeriodStart()` are UNVERIFIED selectors (PRD §3) — do not call them. Use `rewardPeriod(id)` (verified, returns 5 uint256) by probing ids backwards from an env `STAKING_LAST_PERIOD_HINT` or by binary search on `rewardOf(staker, id)` > 0 within the last 168 ids; record what `rewardPeriod` returns for 3 ids in `docs/api-notes.md` and derive which field is the period start. If that cannot be determined in 45 min, fall back to: `settle([])` is NOT allowed; instead expose `settle(periodIds)` with ids supplied by env `STAKING_SETTLE_PERIODS` (comma list) and document it as manual — put the exact question in Blocked on.
- Flow when `STAKER_PRIVATE_KEY` is set: `settle(ids)` (staker) → `claim()` (staker, returns minted amount) → `CREDIT.activate(amount, bytes32(hot))` (staker). Each tx waits 1 confirmation, receipt status checked, `Activated` event decoded (CREDIT ABI) for the activate step. Gates: `TREASURER_LIVE`, `ACTIVATE_MAX_PER_DAY` (default 50 CREDIT = 50e6 atoms, in `policy/defaults.ts`, env may only lower), `MIN_GAS_ETH` on the staker wallet.
- Flow when only `STAKER_ADDRESS` is set: read `settledOf(staker)` and `CREDIT.balanceOf(staker)`; if either > 0, write ONE `alert` treasury event per tick bucket with `meta.manual = {step: 'settle'|'claim'|'transfer', amount, explorerWriteUrl}` (robin.etherscan.io write-contract link) — this is the "manual fallback" the page shows. If `CREDIT.balanceOf(hot)` > 0 and live: `activate(amount)` from the hot wallet (this path needs only `TREASURER_PRIVATE_KEY`).
- CLI `pnpm treasury:claim [--live]` with the same `yes-send` guard as S-05.
- Ledger rows: `dry_run` (with plan) or `settle`/`claim`/`activate` rows with tx hashes; `alert` rows for manual steps.

## Out of scope
- `unstakeAll`/exit (never). Buying (S-05). Policy timing (S-06). Stake-up (S-07).

## Acceptance criteria
1. `planClaim` table-driven tests: live off → dry-run plan; nothing claimable → no-op plan; claimable > cap → capped activate amount with the remainder left in wallet; staker key absent → manual alert plan with correct step; gas floor.
2. `executeClaim` against a fake client: settle→claim→activate called in order with exact args (activate beneficiary = bytes32 hot); a reverted receipt at any step stops the chain and records what completed.
3. Ledger: dry-run → 1 row; full success → 3 rows sharing `meta.idempotencyKey`, each with its own tx_hash; re-call with the same key → no new rows.
4. Live off end to end against the fake client → `writeContract` call count 0.
5. No private key in logs/errors/meta/CLI output.
6. Period discovery documented in api-notes with 3 real `rewardPeriod` reads (live, read-only), or Blocked on filled with the exact question.
7. Live: not in this ticket (first live run is S-06 with So's `ok live`).

## Build notes
Built `packages/core/src/chain/claim.ts` mirroring S-05's `buy.ts` three-layer shape:
- `planClaim()` — pure, overloaded on `input.kind` (`'staker_key' | 'manual' | 'hot_activate'`)
  so each call site gets back only the plan kinds that input variant can produce, no cast
  anywhere. Handles all three flows from "In scope".
- Period discovery: `discoverLatestPeriodId()` (exponential + binary search on
  `rewardPeriod(id)` reverting) and `discoverPeriodsToSettle()` (bounded linear scan of the
  last 168 ids for `rewardOf(staker, id) > 0` — deliberately linear, not binary, since
  "unsettled" ids aren't a contiguous prefix/suffix; see the function's own comment). Resolved
  live within the 45-min time-box (see Evidence) — NOT blocked; `STAKING_SETTLE_PERIODS` is
  still implemented as the ticket's fallback and always wins when set.
- `executeClaim()` (settle→claim→activate, staker-signed) and `executeActivateFromHot()`
  (single-arg `activate(amount)`, hot-signed) — the only two `writeContract` call sites,
  against a narrow `ClaimExecClient`, exercised only by fake clients in tests.
- `claimAndActivate()` — orchestrator. `deps.account` set → runs the automated `staker_key` leg
  alone. `deps.account` unset → runs the `manual` leg (only if `deps.staker` set) AND the
  independent `hot_activate` leg (always attempted) — the ticket's two "if" checks in flow 2 are
  independent, so both can write a row in the same tick (added a `ClaimLegResult[]` return
  shape to represent that, rather than a single result — not explicitly specified by the ticket,
  flagging for audit).
- Shared helpers (`utcDateKey`, `capRemaining`, `addressToBytes32`, `decodeEventFromContract`,
  `requireSuccessReceipt`, a generic gwei-env resolver) went into new `chain/tx.ts`, per the
  ticket's instruction, rather than touching `buy.ts` (never read or edited — confirmed with
  `git diff --stat` after the build that `buy.ts`/`buy.test.ts` are untouched).

  `STAKER_MIN_GAS_ETH` (staker, no PRD number given — see Discovered), `MAX_FEE_GWEI`,

  `ACTIVATE_MAX_PER_DAY = '50'` (CREDIT units).

## Discovered
- The PRD/ticket don't give a gas-floor number for the STAKER wallet specifically (only the
  general "MIN_GAS_ETH" pattern S-05 established for the hot wallet, one tx). Since the
  `staker_key` flow can send up to 3 sequential txs (settle+claim+activate) in one tick, I set
  `DEFAULT_STAKER_MIN_GAS_ETH = '0.0015'` (3x S-05's single-tx default) rather than reusing
  `0.0005` and under-covering the worst case. Flagging for So/PRD: this is a judgment call, not
  a PRD-given number — cheap to change via env either way (`STAKER_MIN_GAS_ETH`).
- Flow 2's two "if" checks (manual alert; hot-activate) are independent in the ticket's prose,
  which the orchestrator's return shape (`legs: ClaimLegResult[]`, 0–2 entries) makes explicit.
  This is new structure beyond what the ticket spells out for the return value — flagging for
  audit in case a simpler single-result shape was expected instead.
- `rewardPeriod`'s 5 fields: derived field[0]=periodStart, field[1]=periodEnd from two
  consecutive periods' boundaries matching exactly + `PERIOD()`'s 3600s gap (solid). field[2]
  vs field[4] (total vs settled reward, my best read) and field[3] (staking weight, out of
  scope for this ticket) are lower-confidence guesses noted in docs/api-notes.md — not relied on
  by any code path (`claim.ts` never reads `rewardPeriod`'s fields 2-4 at all, only uses it as
  an existence probe for discovery).
- No real `STAKER_ADDRESS`/`STAKER_PRIVATE_KEY` exists in this sandbox, so
  `discoverPeriodsToSettle()`'s `rewardOf(staker, id) > 0` half of period discovery is untested
  against live data — fake-client tests only (see Blocked on).

**Major**

2. **`packages/core/scripts/treasury-claim.ts:161`** — `idempotencyKey:
   \`cli-${new Date().toISOString()}\`` is unique to the millisecond on every invocation, so the
   CLI never actually exercises the idempotency check the ticket's AC3/AC4 and Audit focus care
   about ("idempotency key = tick bucket", PROCESS.md §4). Two `pnpm treasury:claim --live` runs

   (`claim.ts:1158-1167`) — nothing here stops a re-run from resending settle/claim/activate. The

   copy this pattern.
3. **`claim.ts:280`** — the `manual` flow's `'settle'` alert step reports `amount:
   input.settledCredit`, which is the ALREADY-settled-but-unclaimed balance, not anything about
   the periods `periodIdsToSettle` that still need settling. If nothing has been settled yet
   (`settledCredit === 0n`) but periods are waiting (`periodIdsToSettle.length > 0`), the alert
   reads "step: settle, amount: 0" — the ticket's Goal calls this fallback "an exact manual
   to-do"; "settle 0 CREDIT" is not exact, it reads as nothing-to-do. `runManualLeg` writes this
   same wrong number into the ledger row's `meta.manual.amount` (`claim.ts:1036`), so it also
   reaches whatever public/alert surface reads that row. `claim.test.ts:284-294` (test 11) never
   asserts `plan.amount` for the `'settle'` case — unlike tests 12/13, which do assert `amount`
   for `'claim'`/`'transfer'` — so this was not caught by the ticket's own test suite.

**Minor**

4. **`docs/api-notes.md:169-172`** — "latest id and latest finalized id are the same read" is
   derived from a single live snapshot (ids 1..82 exist, 83 doesn't, `rewardPeriod(82)`'s
   `periodEnd` already ~1.76h in the past). `discoverLatestPeriodId`/`discoverPeriodsToSettle`
   never check `periodEnd < now` in code — they rely entirely on this one-sample inference that
   "exists" implies "finalized". Per the ticket, settling an unfinalized id is explicitly
   accepted as "fine" (it reverts) — but if the inference is ever wrong (e.g. a period record
   created at period *start* rather than lazily at/after its end), `discoverPeriodsToSettle`
   would sweep the live, unfinalized period into `periodIds`, `Staking.settle(periodIds)` would
   revert as a whole, and `executeClaim` throws before `claim()` ever runs (`claim.ts:634-646`) —
   with no ledger row written for that failed tick (unlike the `refusal`/`manual_alert` paths,
   which do write a row). Not a fund-safety bug (fails closed), but worth a second live
   confirmation before S-06 relies on this daily.
