## Findings

**[Major] F1 — `orders` guard permits 5 mutable columns; PRD says only `status`, and PROCESS.md §4 explicitly checks for this.**
`packages/core/src/ledger/schema.ts:297` (orders `writePolicy.mutableColumns = ['status', 'filled_usd', 'fee_usd', 'resolved_at', 'external_id']`, table def starting line 277) → generated into `supabase/migrations/003_append_only.sql:54-81` (`orders_guard_write`/`trg_orders_guard`) and `packages/core/src/ledger/sqlite/schema.sql` (`trg_orders_guard_update`). PRD.md §9 line 248 states the orders table comment as "`orders -- status is the only mutable column`", and FR-1.1 (PRD.md:103) says "No row is ever updated except `agents.display_*` fields and `orders.status`." PROCESS.md §4 (PROCESS.md:111) literally asks the auditor to check "Are order states mutable only via the executor, and only `status`?" — the answer here is no. This is disclosed in `tasks/T-002.md`'s Build notes/Discovered, attributed to unwritten "ticket concrete guidance" that isn't present anywhere in the committed `tasks/T-002.md` text I read — so as committed, this reads as the builder's own interpretation overriding an explicit "Must" FR, which is exactly the case CLAUDE.md non-negotiable #2 ("PRD wins... follow the PRD and flag the disagreement") is meant to prevent: the PRD's literal spec should have been built (or the wider set proposed *and held for sign-off*), not built directly and merely footnoted. Practically the wider set is close to necessary (an order needs to record its fill price/fee/settlement id somewhere), which is probably why the PRD line is an oversight — but that's a judgment call for So, not the builder, per rule 2. **Verified live**: `update orders set usd = 999` is correctly rejected in both dialects; `update orders set status = 'filled', filled_usd = ..., fee_usd = ..., resolved_at = ..., external_id = ...` is correctly *allowed* in both dialects — i.e. the implementation is internally consistent, just wider than the PRD's literal text.
Recommend: get So's explicit "ok" on the 5-column set in `tasks/T-002.md`'s Sign-off (or narrow it to `status` only and add a separate `orders_settlement` update path/ticket), before this leaves `in-audit`.

**[Major] F2 — `key_meta` has no append-only/guard trigger in either dialect; FR-1.1 lists it among the append-only tables.**
`packages/core/src/ledger/schema.ts:187` (`writePolicy: { kind: 'none' }`, table def starting line 177). Confirmed by direct grep: `key_meta` does not appear anywhere in `supabase/migrations/003_append_only.sql`, and only its `CREATE TABLE` appears in `packages/core/src/ledger/sqlite/schema.sql` (no `trg_key_meta_*`). PRD FR-1.1 (PRD.md:103): "The ledger is append-only. Tables: `agents`, `treasury_snapshots`, `usage_events`, `decisions`, `book_snapshots`, `orders`, `key_meta`. ... No row is ever updated except `agents.display_*` fields and `orders.status`." Read literally, `key_meta` should be just as append-only-protected as `treasury_snapshots`/`usage_events`/`decisions`/`book_snapshots` — instead it currently has **zero** write protection: any writer (service role / a bug in a later ticket's repository code) can silently rewrite or delete `key_prefix`/`key_last4`/`revoked_at`/`reason` history for a key, which is precisely the kind of security-audit-trail table where silent mutation matters most (FR-2.2 key-rotation logging). This is disclosed in `schema.ts`'s doc comment and `tasks/T-002.md` Discovered, attributed to the ticket's own "In scope" bullet ("Triggers rejecting update/delete on **the four** append-only tables") narrowing FR-1.1's seven-table scope down to four — again a ticket-vs-PRD conflict that CLAUDE.md #2 says should resolve toward the PRD.
Recommend: either add the same append-only trigger to `key_meta` (if key rotation is meant to *insert* new rows, per the Discovered note's own suggestion) or get explicit sign-off that key_meta is intentionally exempt, before `in-code`/merge.

**[Minor] F3 — Postgres test suite has two coverage gaps that the SQLite suite doesn't: no test for the `agents` mutable-column guard, and no test for `orders` DELETE rejection.**
`packages/core/src/ledger/schema.postgres.test.ts` has no `describe('agents guard...')` block at all (compare `schema.sqlite.test.ts`'s "agents mutable-column guard" describe block), and its "orders: only status/.../external_id are mutable" block only tests the allow-status and reject-immutable-column cases, not DELETE (compare the SQLite suite's explicit `rejects DELETE` test). I manually verified both actually work correctly in Postgres (`update agents set mode='live'` → `agents: only name, repo_url, x_handle, template, last_seen_at may be updated`; `delete from orders` → `orders rows cannot be deleted`), so this is a **test-coverage gap only, not a functional defect** — but per ADR-002/FR-1.0 ("same tests run against both stores"), the two dialect suites should mirror each other's coverage, and right now they silently don't for these two cases.

**[Minor/Question] F4 — `orders` has no index, unlike every other agent-scoped table.**
`packages/core/src/ledger/schema.ts:277-300` — `orders` is the only table with an `agent_id` foreign key that has no `indexes` array (compare `treasury_snapshots`/`usage_events`, both indexed `(agent_id, ... desc)`). PRD §9's line "Indexes on `(agent_id, as_of desc)`, `(agent_id, at desc)`, `(at desc)` for the feed" doesn't explicitly name `orders`, so this may be intentional (orders aren't part of "the feed"), but `FR-6.1`'s status endpoint needs "open orders count and USD" per agent, which will table-scan `orders` without an index. Flag for T-011/whoever writes the orders repository — not a T-002 blocker, but worth a decision now while the schema is still cheap to change.

**[Minor/Question] F5 — `002_rls.sql` never explicitly grants `USAGE` on the `public` schema to `anon`.**
`supabase/migrations/002_rls.sql` issues `grant select on <table> to anon;` per table but no `grant usage on schema public to anon;`. This worked in my from-scratch vanilla Postgres 16 test only because Postgres ≥15 grants `USAGE` on the `public` schema to the `PUBLIC` pseudo-role by default (`\dn+` showed `=U/pg_database_owner`), and it will also work on Supabase (which grants schema usage to `anon` as part of its own project bootstrap, independent of this migration). Low risk in the actual target environment, but the migration isn't self-contained proof against a cluster with the default schema grant revoked. Consider adding the explicit grant for portability/defense-in-depth.

**[Question] F6 — `RH_CHAIN_ID` is validated/stored as a string, not a number.**
`packages/core/src/env.ts:29` — `RH_CHAIN_ID: z.string().min(1).default('4663')`. ARCH §6 writes it unquoted (`RH_CHAIN_ID=4663`), and `viem` chain configs conventionally want a `number`. Not a defect for T-002 (nothing consumes it yet), but the eventual L2a stake-adapter ticket should either coerce it (`z.coerce.number()`) or explicitly confirm string is intended downstream.

**[Minor] F7 — `orders`' `schema.ts` comment quietly rewrites PRD §9's line rather than flagging the mismatch inline.**
`packages/core/src/ledger/schema.ts:278` — the table's `comment` field reads `'status (and a few settlement fields) is the only mutable data. PRD §9.'`, which is not what PRD §9 actually says (`'orders -- status is the only mutable column'`, PRD.md:248). This is a documentation nit riding on top of F1 — it makes the deviation read as settled/sourced-from-PRD in the generated SQL's own comments (`supabase/migrations/001_schema.sql`'s `orders` table comment inherits this wording verbatim), when it isn't. Fix the comment to say what actually happened (deviation, pending sign-off) regardless of how F1 is resolved.
