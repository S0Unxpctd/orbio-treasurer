### Fixes after audit 1

Built strictly inside `packages/core/src/mcp/{client.ts,schemas.ts,token-store.ts,balance-chain.ts,index.ts}`, plus the three env vars added to `env.ts` (optional) and re-exports added to `packages/core/src/index.ts`. - `token-store.ts`: `McpTokenStore` interface + `EnvFileTokenStore` (atomic write: temp file + `rename`, preserves every other line, `chmod 0o600`) + `InMemoryTokenStore`. Vault store explicitly out of scope (ticket says so) — noted as the seam a future ticket hangs `VaultTokenStore` off.
- `schemas.ts`: Zod schemas for the 4 tools, `.passthrough()` everywhere, only the field each caller actually reads is required (`balance.microUsd`, `hasKey`). `AdapterShapeError` + `recordUnrecognizedSample()` (appends a dated, redacted block to `docs/api-notes.md` "Unrecognized samples", best-effort/never masks the original error).
- `client.ts`: `OrbioMcpClient` — transport (`McpTransport`/`McpTransportFactory`) and OAuth refresh (`OAuthRefresher`) are both injected seams; production wiring (`defaultTransportFactory`, `defaultOAuthRefresher`) is the only place the MCP SDK's HTTP transport and `refreshAuthorization()` are used directly, reusing the same discovery + manual-refresh approach `scripts/probes/p1-mcp-auth.ts` verified (deliberately not the SDK's built-in interactive 401 handler — would block an unattended tick on stdin). Proactive refresh at `expiresAt - now < 5min`; one refresh attempt + one retry on 401; rotated pair persisted via the token store and awaited *before* the new access token is used for anything; MCP_UNAVAILABLE logged once per entry into the unreachable state (client-instance-level edge detection, mirroring `policy/rules/always.ts`'s `computeMcpUnavailable`). `rotateKey(idempotencyKey)` is single-flight per key via a `Map<string, Promise<KeyRotateResult>>` — a concurrent or later retry with the same key joins the original attempt (evicted from the map only on failure, so a successful attempt's result is cached forever and a genuine failure lets a fresh retry actually re-attempt). Key secret extracted defensively from `content[0].text` via regex (structuredContent shape for create/revoke unconfirmed, see Discovered); only `keyPrefix` (16 chars) + `keyLast4` ever leave the client, never the full secret.
- `balance-chain.ts`: `getBalanceViaChain()` — chain is `mcp → estimate`, no `gateway` step (P-2: no key-info endpoint). `estimateBalanceMicroUsd()` is pure BigInt arithmetic over exact microUSD integer strings, reusing `ledger/decimal.ts`'s `normalizeTokenAmount` for validation. `AdapterShapeError` is never caught here — propagates to fail the tick loudly; only unavailability degrades to `estimate` (`lowConfidence: true` always and only when `source === 'estimate'`).

`pnpm lint && pnpm typecheck && pnpm test` all pass. 802 tests total (776 baseline + 26 new: 17 in `mcp-client.test.ts`, 9 in `balance-chain.test.ts`), plus 1 opt-in live test skipped by default.

**[Major] Single-flighted token refresh** (`client.ts`) — `tryRefresh()` is now a thin single-flight wrapper: if a refresh is already in flight (`this.refreshPromise`), every concurrent caller — `ensureFreshToken()`'s proactive path and `callTool()`'s 401 path alike — awaits that *same* promise instead of starting a second one. The check-then-assign happens with no `await` in between (`tryRefresh()` is a plain, non-`async` method), so two callers invoked back-to-back in the same microtask (as `Promise.all` does) can never both observe `refreshPromise === null`. Once the shared attempt resolves, both callers read the fresh pair straight off `this.tokens` (already updated by then) — no separate "re-read the store" step needed, a plain field read gives every joiner the fresh pair for free. The actual refresh work moved into a new private `doRefresh()`, called only from `tryRefresh()`. New tests: 2 concurrent 401s share one refresh with zero `MCP_UNAVAILABLE` (the auditor's exact repro); 2 concurrent proactive-refresh triggers share one refresh too.

**Fail-closed on `tokenStore.save()` failure** (`client.ts`, `doRefresh()`) — if the server refresh call succeeds but persisting the new pair throws, `this.tokens` is deliberately left untouched (old pair, old access token — still valid until it actually expires — keeps serving calls normally, this call itself does not throw). A new `refreshTokenConsumedLocally` flag records that the refresh token is now burnt server-side (P-1: single-use) so `ensureFreshToken()`'s proactive path skips attempting it again on every subsequent near-expiry call (would just hammer the token endpoint with a guaranteed failure); a genuine 401 still gets the normal one-attempt-on-401 treatment, since that's a real server round-trip, not a proactive retry this flag suppresses. Logged once (`mcp-refresh-store-save-failed`, `loggedRefreshSaveFailure` guard). Documented in three separate code comments (the field, `doRefresh()`'s catch branch, `ensureFreshToken()`'s gate) rather than one, since the invariant spans all three. New test: save() throws after a successful server refresh → first call still succeeds off the old token, second (still-near-expiry) call does NOT trigger a second `refresh()`/`save()`, exactly one log line.

**[Minor] `recordUnrecognizedSample()` now wraps `err.message` in `redact()` too** (`schemas.ts`), not only `redactedSample` — defense-in-depth against a future zod version or a custom `.refine()`/`.transform()` message echoing the received value; today's zod never does, but the module no longer leans on that as an unenforced assumption.

`pnpm lint && pnpm typecheck && pnpm test` all pass again. 805 tests total (802 + 3 new: two single-flight concurrency tests + one fail-closed-save test, all in `mcp-client.test.ts`). No live calls made this pass (not needed — pure mocked-transport/refresher tests).

## Discovered

- `orbio_create_key`/`orbio_revoke_key`'s `structuredContent` shape is genuinely unconfirmed — CLAUDE.md's live-call rules forbid calling them against the real MCP here (would rotate So's production key). `schemas.ts` requires only "is an object" for these two; `client.ts` extracts the new key's secret from `content[0].text` via regex (the one thing the tool description guarantees: "The secret is in this response"), not from `structuredContent`. When Orbio's real create_key response is eventually seen (So's human check, or a future ticket with sign-off to call it live), please paste the redacted real shape into `docs/api-notes.md` so `createKeyStructuredContentSchema` can be tightened to require real fields instead of tolerating anything.
- `keyPrefix` length (16 chars) for `key_meta.key_prefix` (PRD §9) is my own choice, not specified anywhere: the literal `"sk-orbio-"` (9 chars) is common to every key, so a naive 8-12 char "prefix" wouldn't actually help anyone tell two rotated keys apart later. 16 chars keeps ~7 identifying characters beyond the shared literal. Flag if So wants a different convention.
- `rotateKey()`'s idempotency is keyed by a caller-supplied string, not automatic — a future executor ticket (T-016?) needs to pass a stable id per rotation attempt (e.g. a decision id or tick id), not a fresh UUID per call, or the dedup guard does nothing.
- `turbo.json` has no `globalEnv`/task-level `env` at all (confirmed by grep) — biome's `noUndeclaredEnvVars` warns on `scripts/probes/p1-mcp-auth.ts`'s `process.env.ORBIO_MCP_URL` read, but that's pre-existing (not introduced by this ticket) and outside T-010's in-scope paths, so left untouched.
