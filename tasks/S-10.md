`@orbio-treasurer/core` first, then `apps/web`, in one command. Verified from a clean `dist/`/
`.next` three times (plain repo-root invocation, from-`apps/web`-with-`cd ../..`, and a final

### Blocker 1 — README "Run it locally" fails as written; its own "no accounts" claim is false
Followed README.md lines 107–125 literally: `pnpm install`, `pnpm --filter @orbio-treasurer/core
build`, `cd apps/web && pnpm dev --webpack` (LEDGER=sqlite, temp `LEDGER_SQLITE_PATH`,
GATEWAY_KEYS set — nothing else), then in another shell `pnpm seed:agent --with-key --label
local` and `curl -s http://localhost:3000/v1/models | jq '.data[].id'`.
Result: `{"error":{"type":"upstream_error","message":"could not load model catalog"}}`, HTTP 502;
`jq` then errors `Cannot iterate over null (null)`. Server log: `Neither TREASURER_PRIVATE_KEY nor
ORBIO_KEY is set` (once `ORBIO_GATEWAY_BASE_URL` is also supplied, the same route throws
`ORBIO_GATEWAY_BASE_URL is not set` first). Neither variable is mentioned anywhere in "Run it
locally". This directly contradicts that section's own sentence: "No accounts, no chain access,
no Supabase — SQLite only" — `/v1/models` and `/v1/chat/completions` both require an Orbio
account key (`ORBIO_KEY`) or a chain wallet key (`TREASURER_PRIVATE_KEY`) server-side to return
anything but an error; there is no documented all-local path (e.g. wiring `ORBIO_GATEWAY_BASE_URL`
to `apps/web/test/fake-upstream.ts`) for a stranger who has neither. Once I supplied both env vars
myself (not per the doc) the mechanism worked correctly end to end (confirmed via a local fake
upstream) — this is a documentation gap, not a code bug in the gateway itself.

### Blocker 2 — docs/DEPLOY.md's own step order defeats step 8's stated purpose
`docs/DEPLOY.md` says "Follow in order" (line 3). Step 8, "Seed the reference agent (once,
**before the first tick**)", says seeding first "avoids the race S-06's tester noted: two
concurrent first-ever ticks both trying to create the same agent row" — but step 8 is placed
*after* step 4 (Cron wiring, which arms the 15-minute `pg_cron` job) and step 7 (First live tick,
`pnpm tick`). Followed in the order the doc gives, cron is already live and a manual tick has
already run before the agent is ever seeded — exactly the unseeded-race window step 8 exists to
close. Move "Seed the reference agent" to before step 4 (or at latest before step 7).

### Blocker 3 — the kit's own default agent fails `npm start` out of the box
README "Use it in 60 seconds" step 3 and `docs/LOOM-script.md`'s 2:25–2:50 segment both chain
`npx create-orbio-agent my-agent --gateway <host> --key otk_...` then `cd my-agent && npm start
&& npm run register`. Reproduced literally (with a real `--gateway`/`--key`, no placeholder):
`npm start` exits 1 with `agent: could not fetch one or more feeds`. Cause: one of the template's
two default `FEEDS` (`https://www.theverge.com/rss/index.xml`) returns HTTP 403 to Node's global
`fetch` — reproduced 3/3 tries — while `curl` to the identical URL from the identical host returns
200 3/3 tries, so it isn't a network-egress restriction of this sandbox; it reads as a
client-fingerprint block Cloudflare applies to Node's default `fetch`, independent of environment.
Because the README/Loom chain the two `npm` commands with `&&`, `npm run register` never runs.
This will reproduce for So during the actual Loom recording unless `FEEDS` is overridden in
`.env`. Fix: swap the default feed, or catch-and-log which feed failed and why instead of the
current blanket `catch { fail('could not fetch one or more feeds') }` in `agent.mjs` (also just a
Minor debuggability note on its own).
