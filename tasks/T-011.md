## In scope
- ledger/types.ts (LedgerStore), ledger/sqlite/*, ledger/postgres/*
- computeSnapshotMetrics(inputs) pure

## Build notes

Files added (all under `packages/core/src/ledger/`, plus one export-list edit):
- `types.ts` — `LedgerStore` interface + per-table `New*`/`*Row` types, hand-kept in sync with
  `schema.ts` (same discipline `gen-sql.ts` uses for the SQL dialects). Only `agents` and
  `orders` get an `update*` method, typed to exactly FR-1.1's mutable-column allow-list; every
  other table gets only `insertX`. `key_meta` revocation is `insertKeyMeta` with `revokedAt`
  set — no update method exists for it at all.
- `decimal.ts` — exact decimal-string arithmetic (parse/format/add/sub/max/divide) on `bigint`
  scaled by 10^6, matching `numeric(18,6)`. Division rounds half-away-from-zero at 6dp. This is
  the one place any arithmetic happens on a money value; everywhere else it's an opaque string.
- `metrics.ts` — `computeSnapshotMetrics(input)`, pure (FR-1.3, FR-3.3): `coverageRatio` (null
  when nothing was spent), `runwayDays` (null = ∞ when accrual ≥ burn, else
  `credits / max(netBurn, ε)`), `burnLowConfidence` (`historyHours < 6`).
- `util.ts` — `newId()` (client-side UUID, used by *both* stores so id generation is never a
  dialect-specific behaviour) and `assertUtcIso()` (rejects any business timestamp not ending
  in "Z").
- `sqlite/store.ts` — `SqliteLedgerStore` + `openSqliteLedger(path)`: creates the parent dir,
  opens the file, sets `PRAGMA foreign_keys = ON`, applies `sqlite/schema.sql` (idempotent,
  `IF NOT EXISTS`) on every open. Uses `better-sqlite3`'s `RETURNING *` so every write returns
  the persisted row in one round trip.
- `postgres/store.ts` — `PostgresLedgerStore` + `openPostgresLedger(connectionString)`. Does
  **not** apply the schema itself (that's `pnpm db:migrate` / Supabase's job — see file header).
  Every mapper explicitly normalizes timestamps with `toIso`/`toIsoOrNull` rather than trusting
  postgres.js's Date-vs-string parsing, so the `IsoTimestamp = string, UTC` contract holds no
  matter what the driver hands back.
- `conformance-suite.ts` — `defineLedgerConformanceSuite(label, openStore)`: one shared set of
  ~19 tests (agents round-trip/update/not-found, key_meta append pattern, FK enforcement, money
  byte-identical at 6dp, usage_events/decisions/book_snapshots round-trips, orders
  insert→fill lifecycle with immutable-field checks, UTC rejection). Not a `*.test.ts` file
  itself — invoked once per dialect.
- `ledger-conformance.test.ts` — runs the suite against `openSqliteLedger(':memory:')`
  (always) and against Postgres only when `TEST_DATABASE_URL` is set, mirroring
  `schema.postgres.test.ts`'s drop-and-reapply-migrations `beforeAll` exactly. No network call
  is made in this sandbox — confirmed by the "skipping" stderr line and by the run finishing in
  37ms with 19 tests skipped, not hung/timed out.
- `metrics.test.ts` — table-driven, covers every case the AC names: zero burn+zero accrual
  (∞), zero accrual (finite), accrual > burn (∞), accrual == burn (∞), the ε floor (default and
  overridden), a value lossy in IEEE-754 to prove no float touches the math, and
  `low_confidence` at 0h / 5.99h / 6h / 24h.
- `decimal.test.ts` — direct coverage of the arithmetic module (not one of the ticket's named
  "Tests required" files, added anyway given the audit focus is explicitly "Float drift").
- `sqlite/store.test.ts` — SQLite-specific: schema-on-first-open incl. nested dir creation,
  idempotent reopen, FK pragma enforcement, and a dedicated **AC4** test that strips every
  `SUPABASE_*` var from `process.env`, opens a sqlite ledger, and completes an insert.
- `index.ts` — re-exports all of the above from `@orbio-treasurer/core`.

Design choices worth flagging for audit:
- **Id generation is client-side for both dialects** (not Postgres's `gen_random_uuid()`
  default), specifically to close the "dialect-specific behaviour leaking above the interface"
  risk named in the ticket's Audit focus.
- **ε has no PRD-given number.** FR-1.3 states the formula but never a value. Defaulted to
  `0.01` USD/day, overridable per call; see Discovered.
- Money/token fields are typed `string` everywhere in `types.ts` (never `number`) — the LedgerStore
  interface itself makes passing a float a type error, on top of `decimal.ts` rejecting a
  malformed string at the repository boundary.

## Discovered

- **No default ε value in the PRD.** FR-1.3 gives `max(burn − accrual, ε)` but never a number.
  Picked `DEFAULT_EPSILON_USD_PER_DAY = '0.01'` (exported, overridable). So: confirm this is a
  reasonable floor for the reference agent's scale, or give me a number.
- **`openPostgresLedger` takes a bare connection string**, not `SUPABASE_URL` +
  `SUPABASE_SERVICE_ROLE_KEY` / `DATABASE_URL` from `env.ts`. Turning the env shape into a
  connection string is env-wiring that belongs to whatever ticket wires `createTreasurer()` to
  a store (not yet ticketed as far as I can see) — flagging so it isn't assumed done.
- **PostgresLedgerStore does not apply migrations.** It assumes `supabase/migrations/*.sql` is
  already applied (via `pnpm db:migrate`), matching how a real hosted deployment works. The
  conformance suite applies them itself in its own `beforeAll`, same pattern as
  `schema.postgres.test.ts`.
- T-011's Postgres path is untested by me in this sandbox — outbound TCP 5432 is blocked here
  by design. It compiles and typechecks, and the exact same 19 conformance assertions that pass
  against SQLite are registered (and skip cleanly) against it; someone with `TEST_DATABASE_URL`
  needs to actually run it once before this is fully trusted.

## Audit report

(211/253, 42 skipped). AC2/AC4 and all §4 checks green. **AC1/AC3 "both stores" claim was
unverified** — the ticket says Postgres was only checked structurally because the sandbox
"blocks TCP 5432," but a **local** cluster needs no outbound network and T-002's own audit
already used exactly that recipe here. I stood one up (`initdb`/`pg_ctl` on `127.0.0.1:55432`)
and ran the real Postgres conformance suite.

- **1 Blocker (B1)**: `PostgresLedgerStore` never `JSON.parse`s `jsonb` columns
  (`decisions.inputs/action/result`, `book_snapshots.view`, `agents.policy`) —
  `SqliteLedgerStore` does. Confirmed live: 2/19 Postgres conformance tests fail
  (decisions round-trip, book_snapshots round-trip); 17/19 pass, incl. AC3's money-6dp
  byte-identical check, which does hold. Exactly the "dialect-specific behaviour leaking above
  the interface" this ticket's own Audit focus names.
- 2 Minor: dead `nowUtcIso()` export (M1); `LedgerStore.dialect` field exposes dialect info
  above the interface, unused today but worth watching (M2).
- 1 Question: ε default (`0.01` USD/day) — PRD gives no number (confirmed by grep); reasonable
  low-stakes default, not blocking.
- Float drift / UTC / CLAUDE.md #4 & #5c: all MET, verified live including against real
  Postgres (numeric columns confirmed returned as strings, never JS numbers).
