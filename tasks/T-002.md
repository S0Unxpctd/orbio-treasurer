# T-002 · Ledger schema (both dialects), RLS, append-only triggers, cron SQL

Day: 0 · Layer: L0 · Estimate: 3.5h · Depends on: T-001 · PRD: PRD §9, FR-1.0, FR-1.1, FR-10.1, ADR-002

## Goal
One schema source generating Postgres and SQLite DDL; append-only triggers in both; RLS for anon reads; pg_cron job SQL; env.ts with Zod.

## In scope
- ledger/schema.ts as source; generated supabase/migrations/001-004 and ledger/sqlite/schema.sql
- Triggers rejecting update/delete on the four append-only tables (both dialects)
- RLS: anon selects public rows only
- 004_cron.sql (requires pg_cron + pg_net enabled)
- env.ts (ARCH §6) with LEDGER/BOOK_CLIENT/STAKE_CLIENT enums

## Out of scope
- Repositories (T-011)
- Application logic

## Acceptance criteria
1. `supabase db push` applies on an empty project; SQLite schema applies on an empty file
2. UPDATE on an append-only table fails in both stores (tests)
3. anon SELECT on decisions returns only public=true (test)
4. cron.job row exists with '*/15 * * * *'
5. Boot refuses on missing required env and names it

## Audit focus
- Money columns: numeric(18,6) in PG, TEXT decimal in SQLite, never REAL
- Schema drift between dialects (must be generated, not hand-written twice)

## Tests required
- integration: schema.test.ts run against both stores

## Build notes
_(builder, 2026-09-08)_
- `packages/core/src/ledger/schema.ts` is the single source: a small typed table/column DSL (`ColumnType`, `WritePolicy`, `RlsPolicy`) describing all seven §9 tables plus the extra `treasury_snapshots` columns named in this ticket (`balance_source`, `stable_balance_usd`, `yield_per_token_per_day`, `yield_low_confidence`) and the two enum CHECKs (`orders.side`, and by extension `agents.mode`, `treasury_snapshots.balance_source`, `book_snapshots.source`, following the same pattern §9 uses for all of them).
- `packages/core/scripts/gen-sql.ts` (run via `pnpm --filter @orbio-treasurer/core gen:sql`) generates, from that one file: `supabase/migrations/001_schema.sql` (tables + indexes + `pgcrypto`), `002_rls.sql` (RLS enable + anon SELECT policies + grants), `003_append_only.sql` (trigger functions/triggers), `004_cron.sql` (static pg_cron/pg_net job — generated for one source of truth even though it isn't schema-derived), and `packages/core/src/ledger/sqlite/schema.sql` (tables + triggers, one file). All five are committed; the header says not to hand-edit them.
- Dialect mapping (ADR-002): money/rates/ratios/percentages/day-counts → `numeric(18,6)` PG / `TEXT` SQLite; on-chain token amounts → `numeric(30,0)` PG / `TEXT` SQLite; timestamps → `timestamptz` PG / `TEXT` ISO-8601 UTC SQLite; booleans → `boolean` PG / `INTEGER` SQLite (CHECKed to 0/1); `jsonb` PG / `TEXT` SQLite. Verified never a float: a SQLite test round-trips a value that's lossy in IEEE-754 (`123456789012.100200`) and a 30-digit token string, both `typeof(...) = 'text'` and byte-identical on read-back.
- Append-only (PL/pgSQL trigger raising, or SQLite `RAISE(ABORT,...)` trigger): `treasury_snapshots`, `usage_events`, `decisions`, `book_snapshots` reject every UPDATE and DELETE. Mutable-column guard (same RAISE-on-violation pattern, generated from a `mutableColumns` list so it can't drift from the four hard-coded append-only tables): `orders` allows `status, filled_usd, fee_usd, resolved_at, external_id`; `agents` allows `name, repo_url, x_handle, template, last_seen_at`. DELETE is always rejected on both. `key_meta` gets no trigger (see Discovered).
- RLS (`002_rls.sql`, Postgres only): RLS enabled on all 7 tables. `agents`/`decisions` — anon SELECT where the row's own `public = true`. `treasury_snapshots`/`usage_events`/`orders` — anon SELECT via `exists (select 1 from agents a where a.id = <table>.agent_id and a.public = true)`. `book_snapshots` — anon SELECT all rows (see Discovered: it has no `agent_id`). `key_meta` — no anon policy at all (RLS default-denies). service_role needs no policy; Supabase grants it `BYPASSRLS`. `grant select ... to anon` added alongside each policy (a policy alone doesn't grant table-level SELECT).
- `004_cron.sql`: `create extension pg_cron/pg_net`, `cron.schedule('treasurer-tick', '*/15 * * * *', ...)` calling `net.http_post` with `current_setting('app.tick_url'/'app.cron_secret')` — no hard-coded URL/secret, comment says the runbook sets those settings.
- `packages/core/src/env.ts`: Zod schema for every ARCH §6 variable (`LEDGER`, `LEDGER_SQLITE_PATH`, `ORBIO_MCP_*`, `BOOK_CLIENT` + its vars, `STAKE_CLIENT` + its L2a vars, `TREASURER_LIVE` via `z.stringbool()`, `LANDING_*`, hosted-only `SUPABASE_*`/`CRON_SECRET`/`NEXT_PUBLIC_SITE_URL`, book-daily `X_*`). `loadEnv()` conditionally requires: `LEDGER=postgres` → `SUPABASE_URL`+`SUPABASE_SERVICE_ROLE_KEY` or `DATABASE_URL` (see Discovered); `BOOK_CLIENT=orbio` → `ORBIO_BUY_URL`/`ORBIO_BUY_TOKEN`; `STAKE_CLIENT=uniswap` → the six L2a chain vars. Throws `EnvValidationError` whose `.message`/`.missing` list variable **names only** — verified by a test asserting no `sk-`/`postgres://`-shaped substring ever appears in the message, and by exact-name assertions for every conditional branch.
- Dependencies: `better-sqlite3` + `@types/better-sqlite3` and `postgres` (porsager) added to `@orbio-treasurer/core`; `better-sqlite3` added to `pnpm-workspace.yaml`'s `onlyBuiltDependencies` (native postinstall build, confirmed it builds non-interactively). `zod` added (not previously a dependency anywhere in the repo). `adr/ADR-005-db-drivers.md` records both drivers and why `postgres` over `pg`.
- `packages/core/src/index.ts` now re-exports the schema types/`LEDGER_SCHEMA` and the env types/`loadEnv`/`EnvValidationError` from the package's public entry point, for T-011 and later tickets.
- Tests: `packages/core/src/ledger/schema.sqlite.test.ts` (18 tests) applies the generated SQLite schema to a temp file and asserts AC1/AC2 plus the money/token exact-decimal round-trip. `packages/core/src/env.test.ts` (11 tests) asserts defaults and every "missing var named, never valued" path. `packages/core/src/ledger/schema.postgres.test.ts` (15 tests) is `describe.skip`-guarded on `TEST_DATABASE_URL`; when set it applies 001-003 against that database, asserts AC1/AC2/AC3 (RLS as `anon` via `set role anon`, including that `key_meta` is unreadable and `book_snapshots` is readable), and checks 004's content/syntax by string (pg_cron/pg_net aren't installed locally, per this ticket's own scope note, so it isn't executed).
- **How to run the Postgres suite** (documented here per the ticket's instruction): start a local cluster as a non-root user (postgres binaries are at `/usr/lib/postgresql/16/bin` in this environment), e.g.:

## Discovered
- **FR-1.1's "agents.display_* fields" doesn't match any §9 column name.** §9 lists `name, repo_url, x_handle, template` (no `display_` prefix) as the closest thing to "display fields." Resolved per this ticket's own concrete guidance ("agents allows updates of display fields and last_seen_at") as `name, repo_url, x_handle, template, last_seen_at`. Flag for So/auditor: confirm this set, or rename the intended columns to actually be `display_*` in a follow-up ticket.
- **`key_meta` gets no append-only trigger**, even though FR-1.1's "no row is ever updated except agents.display_* and orders.status" reads as if it should never be updated either. This ticket's concrete guidance explicitly enumerates only `treasury_snapshots, usage_events, decisions, book_snapshots` (+ orders/agents guards) as needing triggers, so I followed that literally rather than PRD's broader wording. If key rotation (FR-2.2, T-011+) is meant to *insert* a new `key_meta` row per state change (audit-log style) rather than update `revoked_at` in place, this is moot; if not, a follow-up ticket should add the same append-only trigger to `key_meta`.
- **`book_snapshots` has no `agent_id`** (confirmed in §9 — it's global book state, not per-agent), but this ticket's RLS guidance says to gate `book_snapshots` reads "for agents with public = true" like the other three tables. There's no agent to join on, so I made it anon-readable unconditionally (documented in `schema.ts`'s `RlsPolicy` doc and in `002_rls.sql`'s comment). Matches the book being public data anyway; flag for So to confirm.
- **`DATABASE_URL` is not in ARCHITECTURE.md §6's variable list**, but this ticket's guidance requires it as an alternative to `SUPABASE_URL`+`SUPABASE_SERVICE_ROLE_KEY` for `LEDGER=postgres`. Added to `env.ts` and noted in its file comment; ARCH §6 should probably gain this line in a docs pass.
- **Root `pnpm test` is turbo-cached and does not declare `TEST_DATABASE_URL` as a cache-key env var** (`turbo.json`'s `test` task has no `env` field), so running `TEST_DATABASE_URL=... pnpm test` at the repo root can replay a stale cached (skipped) result instead of actually running the Postgres suite — I hit this myself and worked around it with `pnpm --filter @orbio-treasurer/core test` (uncached) instead. `turbo.json` is T-001's territory, so I didn't touch it; a follow-up ticket should add `"env": ["TEST_DATABASE_URL"]` to the `test` task, or the runbook should just always say to use the `--filter` form for this suite.
- Postgres numeric defaults: §9 gives no explicit `numeric` precision for anything other than money/tokens; percentages, rates, ratios and `runway_days` all reuse the `money` (`numeric(18,6)`) column type in `schema.ts` rather than inventing a third numeric type, since the ticket doesn't define one and 6dp is ample precision for all of them. Documented in `schema.ts`'s top comment.
- No default value was added for `agents.mode`, `treasury_snapshots.state`, `treasury_snapshots.balance_source`, `orders.status`, `orders.side`, or `book_snapshots.source` — §9 doesn't specify one for these, so inserts must supply them explicitly; this is a repository-layer (T-011) concern, not a schema one.
