# S-05 · buyAndActivate (gated, capped)
Sprint 1.0 · Layer: L2b · Depends on: S-03 (merged) · PRD: docs/PRD-1.0-sprint.md §3 (Exchange, CREDIT), §4 T-5, §6 gates · MONEY TICKET → Code → Audit → Test

## Goal
In deficit, the Treasurer can buy CREDIT on Orbio's on-chain book with USDG and activate it straight onto its own API balance — only when live is on, only within caps, only when the discount is real — and every attempt (dry or live) leaves a ledger event.

## In scope
- `packages/core/src/chain/buy.ts`: `planBuy(usdgIn, quote, caps, history, now) → BuyPlan | BuyRefusal` — PURE (no I/O; time and history are inputs): refuses when `!TREASURER_LIVE` (plan still returned with `dryRun: true`), when `usdgIn > BUY_MAX_USDG_PER_TX`, when `history.buysToday >= BUY_MAX_PER_DAY` (UTC day), when `quote.creditOut / usdgIn < 1.10` (discount < 10%), when `quote.fills > maxFills`, when the hot wallet's USDG balance < usdgIn or ETH balance < `MIN_GAS_ETH` (env, default 0.0005). `minCreditOut = floor(quote.creditOut × 0.98)`.
- `executeBuy(plan, deps)`: `USDG.approve(exchange, usdgIn)` only if current allowance < usdgIn (read `allowance` first), then `Exchange.buyAndActivate(usdgIn, minCreditOut, bytes32(hot address, left-padded), maxFills)`. Wait for 1 confirmation, decode the `Activated` event from the receipt (CREDIT ABI), return `{txHash, creditOut, activationId}`. Gas: let viem estimate; cap `maxFeePerGas` at env `MAX_FEE_GWEI` (default 5). Private key only from env `TREASURER_PRIVATE_KEY`, never passed around as a string beyond `privateKeyToAccount`.
- Ledger: every call to `buyCredit()` (the orchestrating function) writes exactly one `treasury_events` row: kind `dry_run` with `meta.plan` when not executed (including refusals, with `meta.reason`), kind `buy` with `tx_hash`, `amount` = creditOut (CREDIT atoms), `usd_value` = usdgIn/1e6 when executed; a second row kind `activate` with the same tx_hash and `meta.activationId`. Idempotency: `buyCredit()` takes an `idempotencyKey` (tick bucket); if a `buy` event with that key exists in `meta`, return it without re-sending.
- Caps live in `packages/core/src/policy/defaults.ts` as new constants (`BUY_MAX_USDG_PER_TX = 10`, `BUY_MAX_PER_DAY = 1`, `MIN_DISCOUNT_RATIO = 1.10`, `SLIPPAGE_BPS = 200`) and are overridable ONLY downward via env (`BUY_MAX_USDG_PER_TX` env may lower, never raise).
- CLI `pnpm treasury:buy --usdg 10 [--live]`: prints the plan; sends only with `--live` AND `TREASURER_LIVE=true` AND a typed confirmation `yes-send` on stdin. Not a test target.

## Out of scope
- Policy decision of WHEN to buy (S-06 calls `buyCredit`). `buy()` without activate. Selling. Uniswap.

## Acceptance criteria
1. `planBuy` table-driven tests (≥ 12 rows): every refusal reason, dry-run plan when live is off, minCreditOut math (exact integer), UTC day boundary for `buysToday`, env lowering a cap works and env raising a cap is ignored with a logged warning.
2. `executeBuy` against a fake viem client (mocked `readContract`/`writeContract`/`waitForTransactionReceipt`): approve skipped when allowance suffices, approve sent otherwise; `buyAndActivate` args exactly as specified (beneficiary bytes32 left-padded, minCreditOut, maxFills); `Activated` decoded from a fixture receipt built from the real CREDIT ABI event signature.
3. Ledger rows: dry-run refusal → 1 row kind `dry_run` with reason; success → `buy` + `activate` rows sharing `tx_hash`; idempotent re-call → no new rows, same result (SQLite conformance-style test).
4. With `TREASURER_LIVE` unset, running the whole flow end to end against the fake client never calls `writeContract` (assert call count 0).
5. `MAX_FEE_GWEI` respected in the write request (assert `maxFeePerGas` ≤ cap).
6. No private key material in any log, error, event `meta` or CLI output (redact test + grep).
7. Live: NOT in this ticket. A live buy happens only in S-06's first live run with So's `ok live` in that ticket.

## Discovered
- **MIN_DISCOUNT_RATIO / SLIPPAGE_BPS have no env override**, unlike the ticket's generic
  "overridable ONLY downward via env" sentence might suggest for all four constants. Reasoning:
  for `BUY_MAX_USDG_PER_TX`/`BUY_MAX_PER_DAY`, a *smaller* number is the safer direction (less
  exposure) — exactly what "downward only" protects. For `MIN_DISCOUNT_RATIO`/`SLIPPAGE_BPS`, the
  safer direction runs the *other* way (a lower minimum discount, or higher slippage tolerance,
  is what would be risky) — so a same-named env var would need to be "upward only" to preserve
  the same safety property, which the ticket never asked for. Left both fixed, changeable only by
  a new ticket with So's `ok live`, and documented the reasoning in `policy/defaults.ts`. Flagging
  in case So intended a literal downward override on all four regardless.
- **Idempotency lookup is a linear scan** of the agent's most recent `treasury_events`
  (`eventLookback`, default 200), not an indexed lookup — fine at hackathon scale (≤1 buy/day
  cap), but would need a real index (or a dedicated `idempotency_key` column) if `buyCredit()`
  ever ran at higher frequency. Follow-up ticket, not built here (out of scope).
- **No new live probe was run.** The ticket allows "read-only live calls (getQuote, allowance)
  ... fine for fixtures"; buy.test.ts/buy.ledger.test.ts reuse S-03's already-dated 2026-09-19
  `getQuote(10 USDG, 10)` fixture (`docs/api-notes.md` "S-03 chain reads": `creditOut: 13333332,
  fills: 2`) rather than re-probing the same read. Nothing new to append to api-notes.md.
- The CLI's agent selection (a fixed `default` slug) is a simplification for a single-tenant kit
  instance; S-06's tick will need its own agent-selection story, which this ticket doesn't decide.

## Fix after audit pass 1
Addressed the Major and all three Minor/Question findings from the audit report below. No new
dependency; no schema change (no migration touched).

- **Major (check-then-act race) — closed.** Added `LedgerStore.withAgentLock<T>(agentId, fn)`
  (`packages/core/src/ledger/types.ts`) to the interface, implemented in both stores:
  - `SqliteLedgerStore` (`ledger/sqlite/store.ts`): a per-`agentId` `Map<Id, Promise>` FIFO chain
    gives real, observable in-process serialization for calls sharing an `agentId` (the
    load-bearing guarantee for this kit's single-process deployment), plus a best-effort
    cross-process layer — whichever call finds the connection idle wraps `fn` in a real
    `BEGIN IMMEDIATE … COMMIT/ROLLBACK` (SQLite's actual RESERVED write lock, held for the whole
    call including a live send); a call that arrives while another agent's call already holds
    it runs unwrapped rather than nesting a SAVEPOINT (a released savepoint could otherwise let
    this call's promise resolve and then be silently erased by an outer rollback — rejected as
    unsound). Full reasoning is in the method's own doc comment.
  - `PostgresLedgerStore` (`ledger/postgres/store.ts`): `sql.begin()` around
    `pg_advisory_xact_lock(hashtext(agentId))` — a real, per-agent, transaction-scoped advisory
    lock; a different `agentId` hashes to a different key and never waits on this one.
  - Added to the shared conformance suite (`ledger/conformance-suite.ts`, runs against both
    dialects): two concurrent `withAgentLock` calls on the same agent serialize with observable
    ordering; a different agent is never made to wait; the lock releases after `fn` throws; the
    resolved value passes through unchanged. All pass against SQLite in-memory (Postgres branch
    skips as it already did — no `TEST_DATABASE_URL` in this sandbox).
  - `buyCredit()` (`chain/buy.ts`) now runs its entire body — idempotency lookup, quote/balance
    reads, `planBuy()`, the ledger writes, AND the on-chain send for a live buy — inside
    `store.withAgentLock(agentId, ...)`. New test
    (`chain/buy.ledger.test.ts`, "two concurrent buyCredit() calls..."): two concurrent calls,
    different `idempotencyKey`s, `BUY_MAX_PER_DAY=1`, a fake client with an artificial 30ms
    receipt delay to give a real window for the pre-fix race — asserts exactly one
    `writeContract('buyAndActivate')` call and exactly one `buy` row (the second call correctly
    gets `per_day_cap_exceeded`).
- **Minor 1 (CLI idempotency key) — closed.** `scripts/treasury-buy.ts`'s `idempotencyKey` is now
  `cliIdempotencyKey(now)` → `cli-YYYY-MM-DD` (UTC calendar fields, mirroring `buy.ts`'s own
  `utcDateKey()`), not a timestamp. CLI stays "Not a test target" per this ticket's own scope, so
  no new test file for it.
- **Minor/Question 2 (`MIN_GAS_ETH`/`MAX_FEE_GWEI` directionality) — closed, per So's implicit
  ask via the ticket text ("safety-directional... with a logged warning otherwise").**

  COMMIT/ROLLBACK` wrapping is gone entirely from `SqliteLedgerStore.withAgentLock()`
  (`ledger/sqlite/store.ts`). The per-`agentId` `Map<Id, Promise>` FIFO chain is now the *only*
  guarantee the method makes: same-agent calls in this process serialize, real ordering, lock
  releases on throw; different-agent calls never wait on each other; no DB-level transaction is
  ever opened, so there is nothing for an unrelated write to land inside and no way for it to be
  rolled back by another agent's failure. The method's doc comment is rewritten to state exactly
  that — single-process-per-SQLite-file is this kit's deployment model (`ARCHITECTURE.md`);
  cross-process safety is a Postgres-only property (`pg_advisory_xact_lock`, unchanged, not
  touched by this fix). No fallback layer was kept or reworked — pass 2's own analysis showed
  there is no sound bolt-on fix for a single synchronous connection, only removal or a redesign
  that would add unneeded cross-agent serialization no caller needs.
- **New regression test** (`ledger/sqlite/store.test.ts`, describe block "withAgentLock: SQLite
  has no DB-level transaction wrapping (S-05 audit pass 2)"): reproduces the auditor's exact

  the pre-fix code (checked out the old `store.ts`, ran it standalone: `expected null not to be
  null` — agent B's row was rolled back with agent A's) and passes on the fixed code (agent B's
  row survives regardless of what happens to agent A). Old code restored to the fixed version
  before running anything else.
- The 4 existing `withAgentLock` conformance tests (`ledger/conformance-suite.ts`) are untouched —
  they only assert in-process FIFO semantics (same-agent serialization, different-agent no-wait,

  Green on both dialects (see Evidence).
- `buyCredit()` (`chain/buy.ts`) and S-06's `runTick()` (`tick/tick.ts`, `skipOwnLock`) needed no

### Findings

**Major — `buyCredit()`'s idempotency + day-cap check is check-then-act, not atomic; two
concurrent calls can both pass and both execute.**
`packages/core/src/chain/buy.ts:559-611` (`buyCredit()`). It reads `recent` once (idempotency +
`buysToday`), then later inserts the ledger row(s) — no DB transaction, no unique constraint on
`(agent_id, kind, idempotencyKey)` in `meta` (schema.ts:333-353 has no such index). Two overlapping
`buyCredit()` calls (same or different `idempotencyKey`) both read the pre-buy state, both pass
`planBuy()`'s per-day-cap check, and both call `executeBuy()`, exceeding `BUY_MAX_PER_DAY=1` by
design intent even though each individual call still respects `BUY_MAX_USDG_PER_TX`. This is
exactly the audit checklist's own question ("Can max_buy_usd_per_day ... be exceeded by
concurrency, retries, or a tick running twice?") — answer: yes, in principle. Mitigated today by
(a) no current caller does concurrent calls (S-06's tick isn't built yet; the only caller is the
one-shot CLI), (b) the hot wallet is meant to hold only ~10 USDG (PRD §6), so a second on-chain
buy would likely revert on insufficient balance rather than silently succeed, and (c) same-account
txs serialize by nonce on-chain. Not exploitable today, but must be closed (DB-level uniqueness or
a lock) before S-06 wires this into a cron-fired tick that could genuinely double-fire.

**Minor — CLI's `idempotencyKey` is `cli-${new Date().toISOString()}` (`packages/core/scripts/treasury-buy.ts:149`), unique on every invocation, so it defeats the idempotency
replay-protection for the one path a human actually runs.**
A crash between a successful `executeBuy()` and the ledger write, followed by a manual re-run,
would not be recognized as a replay (day-cap still provides a backstop for a *second* live buy
the same UTC day, but not for a legitimately-intended single retry after a partial failure).
Ticket explicitly marks the CLI "Not a test target," so no AC is unmet, but worth a note back to
So/S-06 since a real tick will need a deterministic (bucket-derived) key, not a timestamp.

**Minor/Question — `MIN_GAS_ETH` env override has no directionality restriction
(`buy.ts:133-142`, `env.ts:101-106`), unlike `BUY_MAX_USDG_PER_TX`/`BUY_MAX_PER_DAY`.** Lowering
it via env weakens the gas-safety floor (the safer direction for a *minimum required balance* is
up, not down — the mirror image of the two caps that are downward-only). Builder's own comment
defends this as "operational tuning, not an exposure cap," which is a defensible reading of the
ticket's exact wording (only the 4 `policy/defaults.ts` constants are called "caps... downward
only" in the ticket), but it is a place a future env misconfiguration could make an underfunded
wallet attempt a tx (still fails safely — a real OOG revert is still caught by the
`status !== 'success'` check, so no fund loss, just wasted gas / a stuck approve). Question for
So: intentional, or should `MIN_GAS_ETH` also be downward-only-hardened?

**Question — `MAX_FEE_GWEI` similarly has no directionality restriction**, same reasoning as
above; same "no fund-loss, only gas-cost" risk profile. No action needed unless So wants it capped
harder.

### Pass-1 findings — verified closed?

**1. Major (check-then-act race) — closed for every real caller today, but the SQLite fallback
layer has a genuine new defect (see Major finding below).**
- Postgres (`postgres/store.ts:329-334`): `withAgentLock` wraps `pg_advisory_xact_lock(hashtext(agentId))`
  in `sql.begin(...)`. `pg_advisory_xact_lock` blocks the calling session until the lock is free and
  auto-releases on `COMMIT`/`ROLLBACK` — verified against the real `postgres` npm client's documented
  behaviour and confirmed empirically: ran the 4 new `withAgentLock` conformance tests against a
  real local Postgres 16 cluster (see Evidence) — same-agent calls serialize with observable
  ordering, different-agent calls never wait, the lock releases after `fn` throws, the resolved
  value passes through. All 4 pass. `fn`'s actual ledger writes (`insertTreasuryEvent` etc.) run on
  `this.sql`, a *different* pooled connection than the one `tx` reserves for the advisory lock —
  correct for an advisory (mutual-exclusion) lock, not a data transaction: the lock still serializes
  correctly because the second caller's own `pg_advisory_xact_lock` call blocks on the same
  connection-agnostic session lock until the first's transaction ends, regardless of which
  connection did the writes. No data-corruption path found here.
- SQLite (`sqlite/store.ts:392-458`): the in-process per-`agentId` `Map<Id, Promise>` FIFO chain
  is correct and is the load-bearing guarantee (verified: two concurrent `buyCredit()` calls,
  30ms artificial receipt delay, real `Promise.all` with no test-side serialization — confirmed by
  reading the test's own call order in JS: both `buyCredit()` calls run synchronously up to
  `withAgentLock`, so call B's chain lookup genuinely observes call A's already-queued promise,
  not a test artifact). Result: exactly 1 `writeContract('buyAndActivate')`, 1 `buy` row, 1
  `activate` row, 1 `dry_run` refusal row — matches the ticket's own claim.
  **However**, the *DB-level* fallback layer (`runLockedTransaction`, same file) is unsound, and
  this is new since pass-1 review only looked at the in-process chain. Repro (ran directly against
  `better-sqlite3`, see Evidence): once one call's `BEGIN IMMEDIATE` is open, ANY other statement
  executed on the same connection — including a *different agent's* "unwrapped" `fn()` writes,
  which the code deliberately does not wrap in its own transaction — becomes part of that SAME
  open transaction, not an independent auto-committed statement. The method's own doc comment
  claims this is safe because of "better-sqlite3/SQLite's per-statement autocommit for each
  individual write `fn` makes" — **that claim is false once a transaction is already open**:
  autocommit only applies when the connection is NOT inside an explicit transaction. Concretely: if
  agent A's live buy is in flight (its `BEGIN IMMEDIATE` open while `executeBuy()` awaits a chain
  receipt for seconds), and agent B's unrelated `buyCredit()` call proceeds concurrently (different
  `agentId`, so no in-process chain wait), B's ledger writes land inside A's still-open transaction.
  If A's `fn()` later throws (chain error, receipt reverted) and the outer code does `ROLLBACK`,
  **B's already-"successful", already-returned-to-caller ledger rows silently vanish** — proven
  with a minimal repro (BEGIN IMMEDIATE → insert "A" → insert "B" → both visible → ROLLBACK → both
  gone). Does not deadlock (better-sqlite3 is synchronous/single-threaded, so there's no lock
  contention, just silent cross-contamination) and does not leave a dangling open transaction on
  throw for the SAME agent (that half is correctly symmetric). **Blast radius today: bounded to
  near-zero** — `ARCHITECTURE.md` line 12/87 states kit deployments (`LEDGER=sqlite`) run ONE agent
  per SQLite file; the hosted multi-agent reference/landing use Postgres (the sound path). So this
  only fires if a single SQLite file is ever asked to hold concurrent live buys for two *different*
  agents — not how the kit is deployed, and not exercised by any current caller (CLI is one-shot;
  S-06's tick isn't built). Still a real, provable bug and a false safety comment in money-adjacent
  code; flagging as **Major** rather than Blocker only because no real caller can reach it under
  the documented architecture. See "New findings" below.

**2. CLI idempotency key = UTC day — closed.** `cliIdempotencyKey(now)`
(`scripts/treasury-buy.ts:15-20`) builds `cli-YYYY-MM-DD` from `getUTCFullYear`/`getUTCMonth`/
`getUTCDate` only — verified no `getMonth`/`getDate`/local getters anywhere in the function, and
it mirrors `buy.ts`'s own `utcDateKey()` exactly. A crash-then-manual-retry within the same UTC day
now replays instead of double-sending. Ticket keeps the CLI out of the test-target list, so no new
automated test — correct per ticket scope, verified by direct code reading only.

**3. `MIN_GAS_ETH` raise-only / `MAX_FEE_GWEI` lower-only — closed.**
`resolveBuyCaps()` (`chain/buy.ts:138-163`): env `MIN_GAS_ETH` only replaces the default when
`envMinGasWei > defaultMinGasWei`; equal is a silent no-op; lower or unparseable both warn and keep
the default. `resolveMaxFeeGweiCap()` (`chain/buy.ts:189-197`): env `MAX_FEE_GWEI` only replaces
the default when `parsed <= DEFAULT_MAX_FEE_GWEI`; higher warns and keeps the default (unparseable
already fell back before this fix and still does). Both directions match the ticket's own
"safety-directional" framing (a floor may only rise, a ceiling may only fall). Verified against the

### New findings (pass 2)

**Major — SQLite `withAgentLock`'s DB-level fallback layer silently merges a different agent's
writes into the lock holder's transaction and can roll them back on the holder's failure.**
`packages/core/src/ledger/sqlite/store.ts:424-458`. See analysis under pass-1 item 1 above. Fix
options for a follow-up ticket: either drop the DB-level layer entirely (the in-process chain is
already the load-bearing guarantee per the code's own comment) and keep it purely in-process, or
make the "arrives while another agent's transaction is open" case genuinely wait (queue) rather
than run unwrapped, instead of relying on a nonexistent per-statement autocommit. Not blocking S-05
under the documented single-agent-per-SQLite-file kit architecture; must be fixed before any code
path runs concurrent multi-agent writes against one SQLite file (tests included — the conformance
suite's own multi-agent fixtures could theoretically hit this if a future test held a transaction
open across an await while seeding a second agent).

**Minor — `buyCredit()`'s own concurrency test (`chain/buy.ledger.test.ts:296-348`) only exercises
SQLite; there is no Postgres-backed equivalent exercising `buyCredit()` end-to-end (idempotency +
day-cap + ledger writes + fake chain client) under the lock.** The generic `withAgentLock` primitive
is tested on both dialects (conformance suite) and `buyCredit()` calls it generically, so this is a
coverage gap rather than a known defect, but it means the specific claim "two concurrent
`buyCredit()` calls, one `writeContract`" has only been proven for one of the two dialects.

**Minor/Question — Postgres `withAgentLock` reserves one pooled connection per held lock
(`sql.begin`), while `fn()`'s own writes use a second connection from the same pool
(`postgres(connectionString)` with no `max` override → default `max: 10`).** At the kit's actual
concurrency (≤1 buy/day cap, one live buy in flight at a time in practice) this is nowhere close to
exhausting 10 connections, but if `buyCredit()` is ever called for ≥10 different agents
concurrently (S-06's tick, at scale) while each also needs a second connection for its writes, the
pool could exhaust and every in-flight call would block waiting for a connection no held
transaction is willing to release — a genuine deadlock, not just contention. No action needed at
current scale; worth a `max` sized to (max concurrent agents × 2) if S-06's tick ever runs many
agents against one Postgres instance.
