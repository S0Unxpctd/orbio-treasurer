# S-05 · buyAndActivate (gated, capped)
Sprint 1.0 · Layer: L2b · Depends on: S-03 (merged) · PRD: docs/PRD-1.0-sprint.md §3 (Exchange, CREDIT), §4 T-5, §6 gates · MONEY TICKET → Code → Audit → Test

## Goal
In deficit, the Treasurer can buy CREDIT on Orbio's on-chain book with USDG and activate it straight onto its own API balance — only when live is on, only within caps, only when the discount is real — and every attempt (dry or live) leaves a ledger event.

## In scope
- `packages/core/src/chain/buy.ts`: `planBuy(usdgIn, quote, caps, history, now) → BuyPlan | BuyRefusal` — PURE (no I/O; time and history are inputs): refuses when `!TREASURER_LIVE` (plan still returned with `dryRun: true`), when `usdgIn > BUY_MAX_USDG_PER_TX`, when `history.buysToday >= BUY_MAX_PER_DAY` (UTC day), when `quote.creditOut / usdgIn < 1.10` (discount < 10%), when `quote.fills > maxFills`, when the hot wallet's USDG balance < usdgIn or ETH balance < `MIN_GAS_ETH` (env, default 0.0005). `minCreditOut = floor(quote.creditOut × 0.98)`.
- `executeBuy(plan, deps)`: `USDG.approve(exchange, usdgIn)` only if current allowance < usdgIn (read `allowance` first), then `Exchange.buyAndActivate(usdgIn, minCreditOut, bytes32(hot address, left-padded), maxFills)`. Wait for 1 confirmation, decode the `Activated` event from the receipt (CREDIT ABI), return `{txHash, creditOut, activationId}`. Gas: let viem estimate; cap `maxFeePerGas` at env `MAX_FEE_GWEI` (default 5). Private key only from env `TREASURER_PRIVATE_KEY`, never passed around as a string beyond `privateKeyToAccount`.
- Ledger: every call to `buyCredit()` (the orchestrating function) writes exactly one `treasury_events` row: kind `dry_run` with `meta.plan` when not executed (including refusals, with `meta.reason`), kind `buy` with `tx_hash`, `amount` = creditOut (CREDIT atoms), `usd_value` = usdgIn/1e6 when executed; a second row kind `activate` with the same tx_hash and `meta.activationId`. Idempotency: `buyCredit()` takes an `idempotencyKey` (tick bucket); if a `buy` event with that key exists in `meta`, return it without re-sending.
- Caps live in `packages/core/src/policy/defaults.ts` as new constants (`BUY_MAX_USDG_PER_TX = 10`, `BUY_MAX_PER_DAY = 1`, `MIN_DISCOUNT_RATIO = 1.10`, `SLIPPAGE_BPS = 200`) and are overridable ONLY downward via env (`BUY_MAX_USDG_PER_TX` env may lower, never raise).
- CLI `pnpm treasury:buy --usdg 10 [--live]`: prints the plan; sends only with `--live` AND `TREASURER_LIVE=true` AND a typed confirmation `yes-send` on stdin. Not a test target.

## Out of scope
- Policy decision of WHEN to buy (S-06 calls `buyCredit`). `buy()` without activate. Selling. Uniswap.

## Acceptance criteria
1. `planBuy` table-driven tests (≥ 12 rows): every refusal reason, dry-run plan when live is off, minCreditOut math (exact integer), UTC day boundary for `buysToday`, env lowering a cap works and env raising a cap is ignored with a logged warning.
2. `executeBuy` against a fake viem client (mocked `readContract`/`writeContract`/`waitForTransactionReceipt`): approve skipped when allowance suffices, approve sent otherwise; `buyAndActivate` args exactly as specified (beneficiary bytes32 left-padded, minCreditOut, maxFills); `Activated` decoded from a fixture receipt built from the real CREDIT ABI event signature.
3. Ledger rows: dry-run refusal → 1 row kind `dry_run` with reason; success → `buy` + `activate` rows sharing `tx_hash`; idempotent re-call → no new rows, same result (SQLite conformance-style test).
4. With `TREASURER_LIVE` unset, running the whole flow end to end against the fake client never calls `writeContract` (assert call count 0).
5. `MAX_FEE_GWEI` respected in the write request (assert `maxFeePerGas` ≤ cap).
6. No private key material in any log, error, event `meta` or CLI output (redact test + grep).
7. Live: NOT in this ticket. A live buy happens only in S-06's first live run with So's `ok live` in that ticket.

## Audit focus

## Discovered
- **MIN_DISCOUNT_RATIO / SLIPPAGE_BPS have no env override**, unlike the ticket's generic
  "overridable ONLY downward via env" sentence might suggest for all four constants. Reasoning:
  for `BUY_MAX_USDG_PER_TX`/`BUY_MAX_PER_DAY`, a *smaller* number is the safer direction (less
  exposure) — exactly what "downward only" protects. For `MIN_DISCOUNT_RATIO`/`SLIPPAGE_BPS`, the
  safer direction runs the *other* way (a lower minimum discount, or higher slippage tolerance,
  is what would be risky) — so a same-named env var would need to be "upward only" to preserve
  the same safety property, which the ticket never asked for. Left both fixed, changeable only by
  a new ticket with So's `ok live`, and documented the reasoning in `policy/defaults.ts`. Flagging
  in case So intended a literal downward override on all four regardless.
- **Idempotency lookup is a linear scan** of the agent's most recent `treasury_events`
  (`eventLookback`, default 200), not an indexed lookup — fine at hackathon scale (≤1 buy/day
  cap), but would need a real index (or a dedicated `idempotency_key` column) if `buyCredit()`
  ever ran at higher frequency. Follow-up ticket, not built here (out of scope).
- **No new live probe was run.** The ticket allows "read-only live calls (getQuote, allowance)
  ... fine for fixtures"; buy.test.ts/buy.ledger.test.ts reuse S-03's already-dated 2026-09-19
  `getQuote(10 USDG, 10)` fixture (`docs/api-notes.md` "S-03 chain reads": `creditOut: 13333332,
  fills: 2`) rather than re-probing the same read. Nothing new to append to api-notes.md.
- The CLI's agent selection (a fixed `default` slug) is a simplification for a single-tenant kit
  instance; S-06's tick will need its own agent-selection story, which this ticket doesn't decide.

### Findings

**Major — `buyCredit()`'s idempotency + day-cap check is check-then-act, not atomic; two
concurrent calls can both pass and both execute.**
`packages/core/src/chain/buy.ts:559-611` (`buyCredit()`). It reads `recent` once (idempotency +
`buysToday`), then later inserts the ledger row(s) — no DB transaction, no unique constraint on
`(agent_id, kind, idempotencyKey)` in `meta` (schema.ts:333-353 has no such index). Two overlapping
`buyCredit()` calls (same or different `idempotencyKey`) both read the pre-buy state, both pass
`planBuy()`'s per-day-cap check, and both call `executeBuy()`, exceeding `BUY_MAX_PER_DAY=1` by
design intent even though each individual call still respects `BUY_MAX_USDG_PER_TX`. This is
exactly the audit checklist's own question ("Can max_buy_usd_per_day ... be exceeded by
concurrency, retries, or a tick running twice?") — answer: yes, in principle. Mitigated today by
(a) no current caller does concurrent calls (S-06's tick isn't built yet; the only caller is the
one-shot CLI), (b) the hot wallet is meant to hold only ~10 USDG (PRD §6), so a second on-chain
buy would likely revert on insufficient balance rather than silently succeed, and (c) same-account
txs serialize by nonce on-chain. Not exploitable today, but must be closed (DB-level uniqueness or
a lock) before S-06 wires this into a cron-fired tick that could genuinely double-fire.

**Minor — CLI's `idempotencyKey` is `cli-${new Date().toISOString()}` (`packages/core/scripts/treasury-buy.ts:149`), unique on every invocation, so it defeats the idempotency
replay-protection for the one path a human actually runs.**
A crash between a successful `executeBuy()` and the ledger write, followed by a manual re-run,
would not be recognized as a replay (day-cap still provides a backstop for a *second* live buy
the same UTC day, but not for a legitimately-intended single retry after a partial failure).
Ticket explicitly marks the CLI "Not a test target," so no AC is unmet, but worth a note back to
So/S-06 since a real tick will need a deterministic (bucket-derived) key, not a timestamp.

**Minor/Question — `MIN_GAS_ETH` env override has no directionality restriction
(`buy.ts:133-142`, `env.ts:101-106`), unlike `BUY_MAX_USDG_PER_TX`/`BUY_MAX_PER_DAY`.** Lowering
it via env weakens the gas-safety floor (the safer direction for a *minimum required balance* is
up, not down — the mirror image of the two caps that are downward-only). Builder's own comment
defends this as "operational tuning, not an exposure cap," which is a defensible reading of the
ticket's exact wording (only the 4 `policy/defaults.ts` constants are called "caps... downward
only" in the ticket), but it is a place a future env misconfiguration could make an underfunded
wallet attempt a tx (still fails safely — a real OOG revert is still caught by the
`status !== 'success'` check, so no fund loss, just wasted gas / a stuck approve). Question for
So: intentional, or should `MIN_GAS_ETH` also be downward-only-hardened?

**Question — `MAX_FEE_GWEI` similarly has no directionality restriction**, same reasoning as
above; same "no fund-loss, only gas-cost" risk profile. No action needed unless So wants it capped
harder.
